# Plan Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the user rearrange their tasks in a preview of the panel (bucket moves, unpins, date changes, order) and then write all of it to their notes with one Apply, or throw it away with Discard.

**Architecture:** A plan is an in-memory overlay on the real index: per-task planned field changes (bucket, due, scheduled) plus a full copy of the saved order, all keyed by the tasks' current real order keys (`file::key`). Every render groups "real lines + planned changes" through the existing `groupTasksIntoBuckets`, so midnight rollover and auto-placement work unchanged. Note edits during planning flow through the same diffs that migrate the real order, applied to the plan as well. Apply writes the planned lines file by file, then replaces the real saved order with the plan's copy, translated old key → new key by line number.

**Tech Stack:** TypeScript, Svelte 5 (legacy syntax), Obsidian API, Jest (pure logic), the ObsidianE2EHarness specs.

**Spec:** [docs/superpowers/specs/2026-11-11-plan-mode-brainstorm.md](../specs/2026-11-11-plan-mode-brainstorm.md). Read it first; this plan argues from it and does not repeat its reasoning.

## Review Focus

1. **Two identical tasks in one note, one of them re-dated by the plan.** After Apply, each keeps its own planned position. Pinned by `translateOrderState keeps duplicate tasks in their planned slots` (Task 8).
2. **The note changes between the plan's last check and Apply** (sync tool, a keystroke during Apply). That file is left untouched, its changes stay planned, and one notice names them. Pinned by `applyLineEdits refuses a file whose expected line moved` (Task 8) and the e2e case in Task 15.
3. **A note with planned tasks is deleted or renamed mid-plan.** Rename: the plan follows. Delete: the changes are dropped and named in the dropped notice; restoring the note (undo the delete) revives them. Pinned by `reconcilePlan drops changes whose task is gone` and `reconcilePlan revives a dropped change when its task returns` (Task 6), and `syncRename moves changes and order to the new path` (Task 6).
4. **Midnight passes during planning.** A planned dated task moves bucket like a real one, and the indicators are recomputed rather than stale. Pinned by `computeIndicators compares against the real grouping of the same day` (Task 7).
5. **A task dragged out and back into its original slot.** The plan reports zero changes and Apply is disabled. Pinned by `planStep drops a field that equals the real value` (Task 3) and `computeIndicators counts nothing for an order equal to the real one` (Task 7).

### Task 3: Plan state and history

```ts
export type PlannedChange = Partial<PlanFields> & {
  /** The bucket change came from a date pick that unpins; "Revert: date" undoes it too. */
  unpinnedByDate?: true;
};
export interface PlanSnapshot {
  changes: Record<string, PlannedChange>;          // entry id → change
  taskOrder: Record<string, OrderEntry[]>;         // full copy, real keys
}
export interface DroppedChange { entryId: string; hash: string; text: string; change: PlannedChange }
export interface Conflict { entryId: string; field: "bucket" | "date"; text: string; file: string }
export interface Plan {
  current: PlanSnapshot;
  past: PlanSnapshot[];
  future: PlanSnapshot[];
  /** Entry ids present when the plan started, carried through rekeys: the tasks Revert can link back to. */
  originals: string[];
  dropped: DroppedChange[];
  /** Entry ids the plan lost (dropped, or a conflict answered "use the note's version"): undo stops at them. */
  lost: string[];
  conflicts: Conflict[];
}
export interface PlanStep {
  /** Per entry: the change to merge in, and the real fields to compare against. */
  changes?: Record<string, { change: PlannedChange; real: PlanFields }>;
  /** Removes this entry from every bucket's order before `order` is written (a cross-bucket move). */
  purge?: OrderEntry;
  order?: { bucketId: string; entries: OrderEntry[] };
}
export const HISTORY_LIMIT = 100;
export function startPlan(taskOrder: Record<string, OrderEntry[]>, entryIds: string[]): Plan;
export function planStep(plan: Plan, step: PlanStep): Plan;   // one undo step; clears `future`
export function undo(plan: Plan): Plan;
export function redo(plan: Plan): Plan;
export function undoBlocked(plan: Plan): boolean;
export function revert(plan: Plan, entryId: string, what: "bucket" | "date", real: PlanFields): Plan;
export function canRevert(plan: Plan, entryId: string): { bucket: boolean; date: boolean };
export function answerConflict(plan: Plan, conflict: Conflict, choice: "note" | "plan"): Plan;
```

Rules the tests pin:
- `planStep` merges each change into the entry's existing change, then deletes every field equal to `real`; an entry left with no field is removed. A step that changes nothing (same changes, same order) adds no history.
- `undoBlocked` is true when the step `undo` would reverse differs, in `changes`, on an id in `lost`.
- `canRevert`: both false for an id not in `originals`; `bucket` true only when the change has `bucket` and not `unpinnedByDate`; `date` true when it has `due` or `scheduled`.
- `revert(..., "date")` removes `due`, `scheduled`, and a bucket marked `unpinnedByDate`. Revert is an undo step.
- `answerConflict(..., "note")` deletes that field from the change (both dates for `"date"`), adds the id to `lost`, removes the conflict. `"plan"` only removes the conflict. Neither is an undo step.
- `past` is capped at `HISTORY_LIMIT`, dropping the oldest.

    - A dropped change whose `hash` matches a current task's key hash, where that task has no change, is revived on that task's id (first match in key order) and leaves `dropped`.

```ts
export type Indicator =
  | { kind: "up" | "down"; by: number }
  | { kind: "bucket-up" | "bucket-down"; fromBucketId: string };
export interface PlanSummary {
  indicators: Record<string, Indicator>;                        // task id → indicator
  deltas: Record<string, { from: number; to: number }>;         // bucket id → open-task counts, only where they differ

}
export function computeIndicators(realGroups: BucketGroup[], planned: BucketGroup[], changedTaskIds: Set<string>): PlanSummary;
```

Rules:
- **Bucket jump:** a task in a different bucket than in `realGroups` gets `bucket-up` if its planned bucket comes earlier in the group list, else `bucket-down`.
- **Order:** within each bucket, take the tasks present in both groupings in that bucket. Their longest increasing subsequence of real positions stays unmarked; every other one gets `up`/`down` with `by` = |real index − planned index| within that common list.
- **Subtask:** no indicator when its parent is in the same planned bucket and also has an indicator, and the subtask still sits directly under it.
- **Deltas:** counts of open (not completed) tasks per bucket; included only when `from !== to`.
- **Count:** tasks with an indicator ∪ `changedTaskIds` (tasks with a planned field change, e.g. a date that keeps the bucket).
